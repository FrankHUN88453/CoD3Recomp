# Player-cap investigation checkpoint — 2026-10-18

## Answer and scope

The 32-player target remains technically plausible. The source study reports that session player masks are 32-bit, so 32 entries fit without changing that message width. Existing 24-player storage has been moved or given reserve capacity in three layers: server-client records (32 x 4,992 bytes, 0.5.210), game-player records (32 x 2,992 bytes, 0.5.208), and session-player records (32 x 784 bytes, 0.5.213). The 0.5.213 solo log showed the session reserve and guard clean during a 20-bot match and map change. These results establish storage headroom for those runs, not functioning player slots 24–31.

No defensible completion percentage is available. Storage is substantially prepared; gameplay integration is still incomplete. The current build remains capped at 24, and `BotsAsk` itself clamps the console request to 20 bots. A 32-player build requires all host and joiner code paths to recognize the same slot range, plus UI and entity checks.

- A trial mapping from catalog address offsets into current generated C did not consistently land on the expected instruction. Prior generated-code patches alter the comment stream, so offset-only matches are not safe evidence. The trial script/report was removed rather than retained as an authoritative audit. Future mapping must reconstruct PPC instruction order with patch-aware alignment and show exact instruction/context before changing any site.
- `CoD3Host/bots.cpp` still defines `MaxClients = 24`, while `BotsAsk` caps requested bots at 20. The 20-bot solo test therefore did not exercise eight extra clients.
- The study still identifies entity numbering, team/spawn assumptions, scoreboard/compass/kill-feed capacity, and any per-client render/animation arrays as unresolved. Solo tests cannot validate the two-PC session protocol path.

## Work required before raising the cap

1. Restore reliable site-to-instruction context from the retail PPC disassembly or implement an alignment-aware mapper that validates itself against unaffected instructions and patch metadata.
2. Classify each genuine player comparison, loop, sentinel store, stride and global base. Mark unrelated constants explicitly so they are never bulk-edited.
3. Audit `bots.cpp`, local-place semantics (including the existing four-local-player limit), entity numbering, server join/leave/respawn paths, and UI capacities. Determine which limits can expand to 32 and which need separate design work.
4. Patch the complete 32-slot path in coordinated stages. Keep a rollback option, guard storage, add boundary checks for slot 23/24/31, and test host-only bot capacity before two-PC System Link.
5. Raise the active cap only after the complete path is covered. Test solo with additional bots, map transition and respawn, then test two PCs on identical binaries.

This is a research checkpoint, not a build. No game code, version number, cap, binary, or install was changed on 2026-10-18.
